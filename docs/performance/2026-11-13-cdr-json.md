# Large CDR byte-array JSON encoding

Arrays of at least 4096 int8/uint8/byte cells can be written directly as numeric JSON arrays, without intermediate boxed integers. Smaller arrays retain the old path. Public DeserializeCDR still returns the original types. The client delivers the same JSON bytes after the existing sanitizer; no fields, rates, coalescing, connection or delivery policy change.

## Paired component measurements

Untouched dev `687260fbd66cf64f689e472fd172fe16ede735b5` versus the CDR-only implementation `bbe06485889d69350f21e6fc259708ac04d5cb0d` (the production code measured here). Intel i7-10700K, Go 1.25.10, GOMAXPROCS=2, process affinity CPUs 2,3, nice 19 and a 1 GiB Go soft memory limit. Five alternating pairs with identical input bytes/seeds. Large-array arms ran 32 operations; the float-array/tiny-byte control ran 512. [Raw paired rows](2026-11-13-cdr-json.csv).

| Fixture | Median time before → after | Paired time reduction, range | Bytes/op before → after | Allocations/op before → after |
|---|---:|---:|---:|---:|
| large | 7.871 → 2.338 ms | 69.3–71.4% | 4,160,858 → 1,516,230 | 119 → 135 |
| mixed | 0.382 → 0.389 ms | -3.7–6.5% | 132,563 → 132,314 | 3944 → 3945 |

`large` is the deterministic 300k int8 fixture, seed 181719, CDR encoding 1, with nested metadata and the full byte domain. `mixed` has 2048 floats and a one-byte tag; it must not select the private writer. The control is about 6 microseconds slower by median, with mixed paired directions; no uniform speedup is claimed. The large case uses more small allocations but about 2.64 MB fewer allocated bytes per message.

Both current GUI topics with sufficiently large byte arrays are grids (mowProgress/lidarMap). At the mow-progress default of one message every 2 seconds, the measured 5.53 ms saving amortizes to about 2.77 ms of component elapsed time per second, before subscriber fanout. This elapsed-time calculation is not a CPU-utilization measurement; the benchmark can include GC and scheduling effects with GOMAXPROCS=2. Actual map sizes and LiDAR publication duty cycle were not recorded.

No network-byte, TCP-packet, reconnect, WiFi or Pi/ARM improvement is claimed. This is an allocation/CPU change at the generic Foxglove boundary, guarded by byte-identity tests against the actual public decoder + sanitizer + encoding/json, including large fixed/nested arrays, malformed inputs and all supported CDR endian/alignment variants.

## Reproduce the component comparisons

From `gui/`:

```sh
GOMAXPROCS=2 go test ./pkg/foxglove -run '^$' \
  -bench '^BenchmarkCDRJSON$/int8_grid_300000/' -benchtime=32x -count=5
GOMAXPROCS=2 go test ./pkg/foxglove -run '^$' \
  -bench '^BenchmarkCDRJSONMixedFloats$' -benchtime=512x -count=5
```

The retained portable benchmarks compare the real original decoder/sanitizer/JSON path and the new path in one binary. The CSV above used separate original/candidate test binaries with the same fixture and benchmark source; absolute timings can differ with binary layout or host conditions. No private network instrumentation is required for these component comparisons. Time results are Go benchmark elapsed ns/op, not measured process-CPU time.
