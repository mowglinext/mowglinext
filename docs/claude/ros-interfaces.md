# ROS Interface Index

> Every topic, service, action, twist_mux lane and TF frame the MowgliNext stack actually creates.
> Index generated 2026-09-03 at f21729e9 — regenerate when nodes are added/removed or a topic is renamed.
> Scope: `ros2/src/**` (excluding `ros2/src/opennav_coverage` and `ros2/src/external`), `ros2/src/mowgli_bringup/launch/*.py` remaps, `tools/motor` (`mowgli_tools`), `sensors/`, and the GUI (`gui/pkg/**`).

## How to use this index

Every name below was grep-confirmed against source at f21729e9 — the `node · file:line` column is where the endpoint is *created*, not where it is documented.
Names are shown **fully resolved**: a node declaring `~/status` appears here as `/hardware_bridge/status`, with the relative name and any launch remap in the notes.
Nav2 / `opennav_docking` / `twist_mux` / GNSS-sidecar endpoints are included where a Mowgli node talks to them; their internals are not enumerated.

`left_wheel_link` / `right_wheel_link` / `front_{left,right}_caster_link` are **continuous** joints in the URDF (`mowgli.urdf.xacro:199,250`) and no `joint_state_publisher` is launched, so they never appear in TF.

**Sole-ownership rule (Inv 2).** Only `fusion_graph_node` may broadcast `map→odom` or `odom→base_footprint`. `wheel_odometry_node` is the one other node that *can* (`mowgli_localization/src/wheel_odometry_node.cpp:96,252`) but its `publish_tf` defaults to `false` and the shipped config pins it there. `ros2/src/mowgli_bringup/test/test_tf_ownership.py` fails the build if any other file constructs a `tf2_ros::TransformBroadcaster`. All Nav2 nodes use `base_footprint` as `robot_base_frame`; `base_link` sits at the rear wheel axis (OpenMower convention — do not move it).

## High-level command/status

`mowgli_interfaces/HighLevelControl` (service `/behavior_tree_node/high_level_control`) and `mowgli_interfaces/HighLevelStatus` (topic `/behavior_tree_node/high_level_status`) are the one command/telemetry pair every external surface uses — GUI, HomeKit, MQTT, the scheduler, the firmware's UI buttons and the drive-PID tuner all call the same service, and the LED ring, hardware bridge, dock calibration and fusion_graph all read the same status topic. The command enum, the state enum, the `state_name` strings, the debounce rules and the area-recording / manual-mowing flows are documented in [`docs/claude/high-level-api.md`](high-level-api.md) — that file is authoritative; this index only records the endpoint names and their wiring.

## Naming conventions

From [`.claude/rules/ros2.md`](../../.claude/rules/ros2.md), as actually practised in the tree:

- **Node-internal topics use relative `~/` names in C++, never the absolute string.** `hardware_bridge_node.cpp` declares `~/status`, `~/power`, `~/cmd_vel`; `map_server_node.cpp` declares `~/mow_progress`, `~/add_area`. The absolute name is a function of the node *name* set in the launch file — e.g. `name="hardware_bridge"` (`mowgli.launch.py:192`) is why `~/status` resolves to `/hardware_bridge/status`, not `/hardware_bridge_node/status`.
- **Remapping happens in launch files, not in C++.** `mowgli.launch.py:258-266` is the single place where the bridge's private names become the shared `/imu/data`, `/imu/mag_raw`, `/wheel_odom`, `/wheel_ticks`, `/cmd_vel` and `/gnss/heading`. Nav2's `cmd_vel` → `cmd_vel_nav` / `cmd_vel_docking` split is likewise a launch remap (`nav2_navigation_launch.py:139,172,229`).
- **Shared system topics are absolute in source.** `/scan`, `/cmd_vel`, `/odometry/filtered_map`, `/gps/fix`, `/gps/status`, `/battery_state`, `/diagnostics`, `/tf` are written as absolute strings wherever they are created or consumed.
- **`/mowgli/` namespace** is used only by `localization_monitor_node` (`/mowgli/localization/mode`, `/mowgli/localization/mode_id`). Everything else is either root-level or under its own node name.
- **Relative names without `~`** resolve against the *namespace* (root), not the node name — `obstacle_tracker_node.cpp:87` publishes `obstacle_tracker/obstacles`, which becomes `/obstacle_tracker/obstacles` only because the string already carries the prefix.
- **The GUI addresses topics by logical key, not by ROS name.** `gui/pkg/providers/ros.go:28-70` is the single `topicMap` from key → `(ROS2Topic, MsgType)`; the browser subscribes via `/api/mowglinext/subscribe/<key>` or the multiplexed socket, and the Go backend translates. Renaming a ROS topic without editing that map silently breaks the GUI, and `"map"` is a *virtual* key with an empty type (populated from `map_server` services, never from a topic).
- **QoS** — sensor data (`/imu/cog_heading`, `/imu/mag_yaw`, `/scan*`, `/gps/fix`) is `SensorDataQoS` (best-effort); commands are `SystemDefaultsQoS` (reliable); status/diagnostics are `QoS(10)` reliable; anything a late-joining consumer must see on connect is `QoS(1).transient_local()` (maps, masks, latched plans, the fusion `set_pose` seed). Two documented exceptions: `/imu/data` is published RELIABLE despite being sensor data, and `/hardware_bridge/dig_event` is `QoS(10).transient_local()` so a rare event survives a subscriber restart.
